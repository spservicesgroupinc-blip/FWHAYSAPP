
# Source bundle import and reconciliation

These tools preserve legacy record IDs, payload values and revisions. File bytes and parsed current/previous snapshot JSON are stored immutably in the private `hays-private` bucket. The `migration_files` table maps their original Drive IDs to storage paths. Apply the reviewed foundation and file mapping migrations before importing. Do not use a source bundle made while staff are writing for final cutover.

1. Assemble and validate the complete source bundle described in `docs/supabase-migration-runbook.md`, including every nonempty previous snapshot and all attachments referenced by current and previous snapshots. Keep it under an ignored protected directory, never in source control.
2. Run `node scripts/supabase-import.mjs <bundle.json>`. This default dry run needs no credentials and performs no network calls. Save the returned sourceDigest securely.
3. Set `SUPABASE_URL`, `SUPABASE_EXPECTED_PROJECT_REF`, and `SUPABASE_SECRET_KEY` in the process environment. The secret must be a server secret or legacy service-role JWT; never a VITE_ variable and never a command argument. Use credentials for the intended isolated rehearsal project, not the live source.
4. To write, set `SUPABASE_IMPORT_SOURCE_DIGEST` to the dry-run digest and run `node scripts/supabase-import.mjs <bundle.json> --apply`. Explicit project-reference validation prevents accidental cross-project writes. Import verifies immutable object bytes by downloading and hashing, inserts mappings and records without upsert, then verifies inserted rows. Existing exact values are accepted on replay; divergent destination values cause an error and are never overwritten. Resume by rerunning the same frozen bundle: every item is rechecked against the destination, with no table-level checkpoint that could skip partial work. A lost upload or insert response is handled the same way.
5. Run `node scripts/supabase-reconcile.mjs <bundle.json>` with the same environment. This reads the actual destination, compares all expected record IDs/payloads/revisions/timestamps, rejects extra rows or mappings and verifies stored object hashes. Any difference or request failure exits nonzero. Equal counts alone are not a pass.

The tools do not configure Auth, grant staff access, freeze source writers, or switch the frontend. The service credential bypasses RLS; validate end-user authorization independently. They do not enumerate additional Drive history or orphaned files absent from the supplied bundle. Only supplied parsed snapshot JSON is archived, not the original JSON text formatting. Migration receipts preserve source mutation envelopes inside those snapshots; legacy mutation IDs are not activated as new user's operation receipts.

The importer is deliberately insert-only. Do not import a rehearsal into a destination that will accept staff writes before final migration. A changed source after rehearsal requires an explicit reconciliation/cutover strategy or a clean, isolated destination, rather than overwriting destination edits. No automated cleanup or deletion is performed. Back up database and object bytes independently before making operational changes.
